# 06 DS18B20 温度水印叠加到摄像头画面

> 目标：**开机自动在 LCD 的摄像头画面上叠加一块温度水印**，读数来自板载 DS18B20，
> 全程不需要手工加载驱动或启动程序。
>
> 完成时间：2026-11-27

---

## 一、最终效果

冷启动后（无任何人工操作）：

```
上电 → 内核 → cramfs → rcS
     → insmod ds18b20_drv.ko
     → insmod uvcvideo.ko
     → sleep 3
     → 守护循环启动 uvc2fb
     → LCD 实时画面 + 左上角 T=xx.xC 水印
```

实测截图见 [uvc_temp_watermark.png](uvc_temp_watermark.png)（800×480 原始帧缓冲导出）。

水印样式：

```
┌──────────────────┐
│ T=28.6C          │   ← 白字黑底，字高 35 像素
└──────────────────┘
```

## 二、硬件确认：DS18B20 到底接哪个引脚

编译驱动前先核对原理图，避免用错引脚（达内驱动包不一定对所有引脚都适配本板）。

`docs/hardware/schematic/CW210-Peripherial_底板.pdf` 第 6 页「传感器电路」：

| 项 | 原理图 |
|---|---|
| 器件 | U20，DS18B20（TO-92） |
| pin1 | GND |
| pin2 | **DQ → XEINT8** |
| pin3 | VDD |
| 上拉 | R20 = 4.7K 到 3V3_IO |

S5PV210 上 `XEINT8 = GPH1_0`，与达内驱动 `ds18b20_drv.c` 里的
`gpio_request(S5PV210_GPH1(0), "GPH1_0")` **完全一致**，无需改引脚。

> 顺带确认：红外接收头 HS0038B 用的是 **XEINT6（GPH0_6）**，与温度传感器不冲突。

## 三、驱动编译

源码取自培训资料 `drivers.tar.bz2` 的 `drivers/ds18b20/ds18b20_drv.c`，
按**外部模块**方式编译（不改内核源码树）：

```makefile
# Makefile
obj-m := ds18b20_drv.o
```

```bash
make -C ~/kern M=$PWD ARCH=arm CROSS_COMPILE=arm-linux- modules
```

产物 `ds18b20_drv.ko` = 3,814 字节，vermagic：

```
2.6.35.7-Concenwit preempt mod_unload ARMv7
```

与板内运行的内核严格匹配。

### 对原驱动做的两处修改

| 位置 | 原代码 | 改成 | 原因 |
|---|---|---|---|
| `ds18b20_reset()` | 成功也 `printk("reset ok.\n")` | 只在失败时打印 | 每秒打印一次会刷爆 dmesg，**并触发 fbcon 重绘把水印盖掉**（见第五节） |
| `ds18b20_read()` | `mdelay(750)` | `msleep(750)` | `read()` 在进程上下文，可以睡眠；`mdelay` 是忙等，会让读取进程占用 43% CPU |

修改后的 `printk`：

```c
if (ret != 0) {
        printk("ds18b20: reset failed.\n");   /* 只在异常时打印，避免刷屏 */
}
```

### 设备接口

- 混杂设备 `/dev/ds18b20`（misc，动态次设备号）
- `read()` 返回 4 字节 int，单位 **0.0001℃**

```bash
dd if=/dev/ds18b20 bs=4 count=1 | od -An -tu4
# 输出 285625 → 28.5625 ℃
```

> `read()` 内部会先发转换命令再 `msleep(750)` 等转换完成，所以**一次读要 750ms**，
> 这是 DS18B20 12 位精度的固有转换时间，无法缩短。

## 四、水印实现

### 4.1 数据流

```
fork 子进程 → /dev/ds18b20 读温度 → 写入 mmap(MAP_SHARED|MAP_ANONYMOUS)
                                          ↓
主进程每帧：YUYV → RGB → 写 fb0（跳过水印矩形）→ 画水印
```

温度读取放到子进程，是因为 `read()` 要阻塞 750ms，放在主循环会让画面卡顿。

### 4.2 点阵字体

内置 5×7 点阵（只覆盖 `0-9 . C T = - 空格`），放大 **5 倍** → 单字 25×35 像素：

```c
static const struct glyph g_font[] = {
    {'0', {0x0E, 0x11, 0x13, 0x15, 0x19, 0x11, 0x0E}},
    {'T', {0x1F, 0x04, 0x04, 0x04, 0x04, 0x04, 0x04}},
    ...
};
```

### 4.3 固定水印区域（关键设计）

```c
#define WM_X      8
#define WM_Y      8
#define WM_PAD    6
#define WM_SCALE  5
#define WM_MAXCH  8                                   /* 最长为 "T=-12.3C" */
#define WM_W      (WM_MAXCH * (5 * WM_SCALE + WM_SCALE) - WM_SCALE + WM_PAD * 2)
#define WM_H      (7 * WM_SCALE + WM_PAD * 2)
```

- 水印占用固定矩形 **(8,8) ~ (255,55)**，宽度按最长字符串预留
- 每帧先整块涂黑，再画白字（字数变化不会残留笔画）
- **像素转换时跳过该矩形**，见下节

## 五、三个导致「水印看不见」的坑

### 坑 1：fbcon 抢屏

驱动的 `printk("reset ok.")` 每秒一次 → 内核控制台（framebuffer console）在 `/dev/fb0` 上
重绘文字 → 水印刚画好就被覆盖。

现象：屏幕左上角出现几段白色短横线（console 文字的残影）。

处理：

```c
/* 解绑 framebuffer 控制台 */
for (i = 0; i < 4; i++) {
    snprintf(p, sizeof(p), "/sys/class/vtconsole/vtcon%d/bind", i);
    fd = open(p, O_WRONLY);
    if (fd < 0) continue;
    write(fd, "0", 1);
    close(fd);
}
```

> 注意：实测这个内核上写 `0` 后 `cat bind` 仍返回 `1`，解绑**没有真正生效**。
> 真正解决问题的是**给驱动静音**——没有内核打印，fbcon 就不会重绘。

### 坑 2：每帧被自己的转换覆盖（最关键）

原流程是「转完整帧 → 画水印」。但下一帧的转换从 `y=0` 开始立刻重写整屏，
水印区域在 **约 1ms 后**就被覆盖。

结果：水印确实每帧都画了，但只有约 1/30 的时间可见，抓图几乎永远抓不到。

**正确做法：转换时跳过水印矩形**

```c
for (x = 0; x < fb_w; x++) {
    /* 水印区域不参与转换，否则每帧都会被画面覆盖掉 */
    if (x >= WM_X && x < WM_X + WM_W &&
        y >= (unsigned int)WM_Y && y < (unsigned int)(WM_Y + WM_H))
        continue;
    ...
}
```

这样水印画一次就稳定保留，且不闪烁。

### 坑 3：子进程泄漏（会导致 rmmod 失败）

`fork()` 出的温度读取子进程会：

1. **继承父进程的 `/dev/video3` 句柄** → 父进程退出后设备仍被占用，`VIDIOC_S_FMT` 报 `Device or resource busy`
2. **继承父进程的 SIGTERM 处理器** → `killall` 杀不掉，因为信号被父进程的 handler 吞掉

正确写法：

```c
g_temp_pid = fork();
if (g_temp_pid == 0) {
    int fd;
    /* 子进程必须恢复默认信号处理，否则会被父进程的 SIGTERM 处理器“吞掉”而杀不死 */
    signal(SIGTERM, SIG_DFL);
    signal(SIGINT,  SIG_DFL);
    signal(SIGHUP,  SIG_DFL);
    /* 关闭从父进程继承的 video / fb / 日志句柄，否则会一直占着设备 */
    for (fd = 3; fd < 64; fd++) close(fd);

    fd = open("/dev/ds18b20", O_RDONLY);
    if (fd < 0) _exit(0);           /* 没有驱动就退出，父进程不显示温度 */
    for (;;) {
        int v = 0;
        if (read(fd, &v, sizeof(v)) == (ssize_t)sizeof(v))
            *g_temp = v / 10000.0f;
        sleep(1);
    }
}
```

## 六、rcS 集成

`/etc/init.d/rcS` 末尾：

```sh
# ---- DS18B20 温度传感器驱动 ----
[ -e /lib/modules/ds18b20_drv.ko ] && insmod /lib/modules/ds18b20_drv.ko

# ---- USB 摄像头开机自启（守护重启，画面叠加温度水印） ----
[ -e /lib/modules/uvcvideo.ko ] && insmod /lib/modules/uvcvideo.ko
sleep 3
(
    while true; do
        /usr/bin/uvc2fb > /tmp/uvc.log 2>&1
        sleep 3
    done
) &
```

顺序要求：**温度驱动必须在 uvc2fb 启动前加载**，否则程序启动时 `/dev/ds18b20` 还不存在，
子进程会直接退出、整轮运行都不会再显示温度。

## 七、打包与烧录

### 7.1 重新打包 cramfs

```bash
# 1. 解包当前镜像
cramfsck -x ~/cram/root ~/cram/cur.cramfs

# 2. 放入新文件
cp uvc2fb            ~/cram/root/usr/bin/uvc2fb
cp ds18b20_drv.ko    ~/cram/root/lib/modules/
# 修改 ~/cram/root/etc/init.d/rcS

# 3. 以 root 身份打包（保证文件属主是 0:0）
cd ~/cram/root
unshare -r mkcramfs ~/cram/root ~/cram/out.cramfs

# 4. 校验
cramfsck out.cramfs
```

本次产物 3,944,448 字节（原 3,940,352），`cramfsck` 输出 `OK`。

> 工具获取：`cramfsprogs` 在新版 Ubuntu 已移除，可直接下载 deb 解包用，无需 root：
> ```bash
> curl -O http://archive.ubuntu.com/ubuntu/pool/universe/c/cramfs/cramfsprogs_1.1-6ubuntu1_amd64.deb
> dpkg-deb -x cramfsprogs.deb ./root
> ```

### 7.2 u-boot 烧录

```text
setenv ipaddr 192.168.1.6
setenv serverip 192.168.1.13
tftp 0x30000000 rootfs_wm.cramfs          # Bytes transferred = 3944448 (0x3c3000)
nand erase 0x700000 0x400000
nand write 0x30000000 0x700000 0x3c3000  # 4063232 bytes written: OK
```

**注意：3.9MB 走 TFTP 约需 15~40 秒**，命令要等 `Bytes transferred` 打印后再发下一条。
本次曾因为等待时间不够，`nand erase` 被串口缓冲排队，在 tftp 仍未完成时处于待执行状态——
一旦 tftp 超时退出就会**自动擦除 rootfs**。所幸及时断电清空了缓冲。

> 教训：烧录脚本里 tftp 的等待时间要给足（45 秒），并且**擦除/写入命令必须单独一次发送**，
> 确认 `Bytes transferred` 后再执行。

### 一次 USB 抖动与自动恢复

开机约 90 秒时：

```text
uvcvideo: Failed to resubmit video URB (-27).   ×5
device: 'ep_82': device_unregister      ← 摄像头从 USB 总线上掉线
device: 'ep_82': device_add             ← 重新枚举
```

画面中断约 15 秒，随后：

1. `uvc2fb` 检测到连续 12 秒无帧 → 主动退出
2. 守护循环 3 秒后重启
3. 自动恢复出图

属于 USB 供电/hub 层面的偶发掉线，之前手动运行 20 分钟也出现过一次。
若频繁发生，建议给摄像头加**带外部供电的 USB HUB**。
