## 一、起点的三道硬约束

| # | 约束 | 具体表现 | 被迫采取的做法 |
|---|---|---|---|
| 1 | 三星 USB 驱动装不上 | Win11 家庭版 x64，设备管理器「SEC S5PC110 Test B/D」黄色感叹号 | 放弃内核驱动，改**用户态 libusb** 自己实现 DNW |
| 2 | 网口不通 | RJ45 指示灯从未闪过；板子无 IP，tftp/nfs 全部不可用 | 放弃网络，改为 **mini-USB + 串口** 双通道 |
| 3 | 每轮都要手工 RESET | 内核一旦跑挂，USB 设备"枚举在但不吃数据"，软件无法自愈 | 每轮必须**有决定性产出**；脚本必须能自动恢复 |

第 3 条是最贵的约束。它直接决定了后面所有脚本的设计原则：**一轮只验证一件事，验证完立刻把结论落到文件**，而不是"再跑一次看看"。

## 二、第一战场：驱动——为什么最终是"自己写一个 DNW"

### 2.1 排查链条

| 候选 | 核查方式 | 结论 |
|---|---|---|
| 培训包 `resource/day01/x210 usb Driver/secusb2.inf` + `secusb2.sys` | 读 PE 头 | `.sys` 是 **PE machine 0x014c（x86）**，Win11 x64 内核无法加载，**与签名、与家庭版都无关** |
| `resource/day01/.../wceusbsh.sys` | 同上 | 同样是 32 位 |
| `arm/x210_android_driver.rar` | 解包看 INF 的 VID/PID | Google WinUSB 驱动，只覆盖 `0BB4/18D1/22B8`，与本设备 `04E8:1234` 无关 |
| GitHub 搜 `secbulk` / `s5pv210 dnw` / `x210 usb driver` | 逐个仓库看 | 只有 2 个结果且都是 **Linux 侧 `secbulk.ko`**；`s5pv210 dnw`、`x210 usb driver` 均 0 结果 |
| X210 完整光盘 `A盘\tools\USB驱动\dnw_driver_win7-64\inf64\secbulk.inf` | 培训包里比对 | **64 位版确实存在，但培训包未收录**（手上没有这张盘） |

### 2.2 解法：Zadig + 用户态 DNW

用 **Zadig 把 `04E8:1234` 绑到 WinUSB**，再用 `pyusb + libusb`（64 位 DLL）在用户态实现 DNW 协议。绕开内核驱动，也就不需要签名。

> 这一步的意义被严重低估：**能往 `0xD0020010` / `0x23E00000` 写数据，等于 u-boot 可以被无限次重新装上**。后面所有"可能把板子跑死"的破坏性实验，都靠这条退路撑着。

## 三、工具链的两个轮子

### 3.1 `dnw.py` —— USB 裸机下载

| 项目 | 值 |
|---|---|
| 设备 | `VID:PID = 04E8:1234` |
| 端点 | `0x02` OUT / `0x81`、`0x82` IN |
| 包格式 | 4 字节地址 + 4 字节总长(N+10) + 载荷 + 2 字节 `uint16` 校验 |
| 分包 | 512 字节 bulk |
| BL1 目标 | `0xD0020010`（有头的 `x210_usb.bin`） |
| BL2 目标 | `0x23E00000`（`u-boot_nomenu.bin`） |

**踩出来的经验规律：内核跑挂一次之后，设备会"枚举在但不吃数据"（第一包就超时），只能物理 RESET。**
这条规律是后来所有"一轮一复位"脚本设计的直接原因，也是为什么每轮都必须武装看门狗。

### 3.2 `ymodem.py` —— 串口传文件

| 环节 | 要点 |
|---|---|
| 握手 | 等 u-boot 发 `'C'`（0x43） |
| 0 号块 | `SOH` + 128 字节，含文件名 + 长度 |
| 数据块 | `STX`（1024 字节）+ CRC16-XMODEM |
| 结束 | `EOT` |
| **收尾** | **必须再补一个全 0 的 0 号块** |

最后一条是最容易漏的坑：不补全 0 块，**u-boot 会停在批量接收模式，后续所有命令都会被当成 YMODEM 数据吞掉**，表现为"传完了但敲什么都没反应"。

另外两个非坑的"假警报"：

- 会看到 `第 1 块重试 1（收到 67）`——67 就是 `'C'`，属正常的双 `'C'` 现象，不用管。
- **FTDI 的 DTR/RTS 在关闭串口时会复位板子**。而 u-boot 这时只在内存里（两阶段 USB 装入），一复位就没了。所以必须**一次开串口、全程不关**，把「装 u-boot + 擦除 + 传文件 + 写 NAND」放进同一个进程里做完。这是 `serial_flash.py` 存在的原因。

实测速率：**10.2 ～ 10.4 KB/s**（115200，1K 块）。

## 四、"不用网口，只靠串口能不能烧" —— 已验证：能

这是被用户明确逼出来的问题（"我怀疑网口有问题，能不能不通过网口烧录，就通过串口烧录"）。

| 对象 | 大小 | 目标 | 结果 |
|---|---|---|---|
| `zImage` | 4,261,256 B | NAND `0x500000` | `4325376 bytes written: OK` |
| `rootfs.cramfs` | 3,301,376 B | NAND `0xA00000` | `3407872 bytes written: OK` |
| rootfs 回读 | — | `nand read` + 校验 | CRC32 = `afc69de9`，**与 PC 完全一致** |

**结论：串口完全可以替代网口完成 NAND 烧写。** 下篇整篇都建立在这个结论上。

同时期的三个硬事实：

| 事实 | 说明 |
|---|---|
| `nand read/write` 长度必须 128KB 对齐 | 否则报 `ERROR: Length (0x1000) is not block aligned` |
| u-boot 内建 `dnw` 命令不可用 | 传完板子就挂，弃用 |
| 原厂 `bootcmd` 里的 `0xc0008000` 在这块板上读回是乱码 | 改用 `0x40000000`（这个地址实测可靠） |

## 五、第三战场：内核"静默"的排查方法论（本篇核心）

### 5.0 第一条原则

> **静默 ≠ 没跑。** 内核在 `console_init` 之前没有任何输出能力，`start_kernel` 里任何一步挂死都表现为"一个字都没有"。

整个 11-25 都在和这条原则搏斗。下面这七种手法是那次搏斗的沉淀，下篇还在用。

### 5.1 七种手法

| # | 手法 | 能回答什么问题 | 硬件成本 |
|---|---|---|---|
| 0 | **裸机点灯/蜂鸣器**（`led.bin`） | 「我能不能往 DRAM 放代码并让它跑起来」——最小链路验证 | 1 次复位 |
| 1 | **二进制取证** | 解压 zImage，按结构找 `machine_desc`、预留表、`CONFIG_CMDLINE`、常量 | **0**（纯离线） |
| 2 | **自建 ATAGS 桩** | 绕开 u-boot 传参的不确定性，自己决定 `r0/r1/r2` 和 cmdline | 1 次传输 |
| 3 | **读 `__log_buf`** | panic 后日志已经刷进 DRAM，`md.b` 捞出来还原 | 1 次复位 |
| 4 | **裸机死循环探针**（`b .`） | 区分「代码产生的输出」和「环境产生的输出」 | 1 次复位 |
| 5 | **内存测绘桩**（`memtest.S`） | 别名周期测真实可用容量 | 1 次复位 |
| 6 | **寄存器取证 / 位域解码** | BL1 到底声明了多少内存、怎么声明的 | 1 次复位 |
| 7 | **标记探针**（`tramp_probe.S`） | 挂死在内核的哪一条指令附近 | 多次 |

手法 7 在上篇只开了个头，**下篇第三章把它做成了完整体系**——在 `stext` 上打 `P Q A C D F G M H` 一串标记，把"静默"变成"知道死在哪一页"。

### 5.2 手法 2 的三个必须记住的地址教训

| 坑 | 现象 | 原因 / 修复 |
|---|---|---|
| ATAGS 放 `0x2FE00000` | 内核零输出 | 离内核 240MB，落在 `head.S` 初始页表覆盖外，MMU 一开就取数异常且无任何调试输出。**必须放 `0x20000100`**（u-boot 自己的 `boot_params`） |
| 镜像放 `0x24000000` | 板子直接死 | `0x23E00000` 紧邻其上方是 **u-boot 自己的 malloc/栈区**，写 4MB 把 u-boot 踩死 |
| `nand read` 到 `0x24000000` | 同上 | 同上，改到 `0x21000000` |

换成 `0x20000100` 之后，解压器第一次成功打印出 `Uncompressing Linux... done, booting the kernel.` —— 这是整晚的第一个正向信号。

### 5.3 环境侧踩的坑

| 坑 | 表现 | 处理 |
|---|---|---|
| 残留 python 进程占串口 | `PermissionError(13, '拒绝访问')` 打不开 COM3 | `Get-CimInstance Win32_Process` 查 PID 后 `Stop-Process -Force` |
| `wmic` 不存在 | `FileNotFoundError: [WinError 2]` | 改用 `Get-CimInstance` |
| PowerShell `Add-Type` 被安全策略禁止 | 想用 .NET 裁剪图片失败 | 放弃，直接用图片查看工具 |
| `pip install pillow` 装不上 | `No matching distribution found` | 同上 |
| `md.b` 输出没吐完就开新串口 | 读到上一轮的十六进制残留，误判 DEAD | 先循环读空再发 `\x03\r` |

## 六、被推翻的结论清单（本节最值钱）

上面这些手法用下来，**一共产生了 8 个错误结论**。全部列在这里，是为了下次不要重走。

| # | 当时的结论 | 当时的依据 | 后来怎么被推翻 | 真相 |
|---|---|---|---|---|
| 1 | machine ID 不匹配（内核要 `0x3F80`，u-boot 传 `0x998`） | 从 `.proc.info.init` 与 `.taglist.init` 之间解出 `machine_desc.nr = 0x3F80` | `bdinfo` 显示 `arch_number = 0x998`，且内核确实进得去 | `0x998`(SMDKV210) 是对的，解出的 `0x3F80` 是别的结构 |
| 2 | NAND 里的 u-boot 环境变量损坏 | 启动行为异常 | `setenv`/`saveenv` 一直正常 | env 从来没坏过 |
| 3 | 物理内存 256MB / 512MB 可用 | `bdinfo` 声明 bank0/bank1 各 512MB | 别名周期精确 = 128MB；内核日志 `On node 0 totalpages: 32768` = 128MB | `bdinfo` 是**编译期声明**，不是探测结果 |
| 4 | u-boot 的 DMC 参数是某个构建的 bug | DMC0 `row=16bit` 而 DMC1 `row=14bit`，两通道不一致 | 换 2014 版 u-boot，`bdinfo` 输出**完全一样** | 原厂就是这么配的，不是 bug |
| 5 | **128MB 是硬上限** | 别名周期 + `totalpages` | 下篇实测：**1GB DDR2（8 × K4T1G084QQ）**，u-boot 自报 `This Board: SDRAM is 1024MB` | 128MB 只是 ATAGS 传的那个值 |
| 6 | 预留表 154.8MB 导致 bootmem OOM，是真因 | 表内 10 项合计 154.8MB > 128MB，且日志显示分配到约 130MB 就 `failed` | 清零前 6 项（137.7MB）重新打包后**依然不启动** | 真因是**内核自带三分区表与 cmdline 不一致**（下篇第五章） |
| 7 | `OKOKOK...` 是波特率不匹配的解码垃圾 | 内核镜像里搜不到独立 `OK` 字符串 | ①对 256 个字符 × 599 种波特率比例穷举模拟，**前 4 字符命中数 = 0**；②跳一个**纯死循环 `b .`**（完全不碰 UART）**仍然冒出 `OK`** | **已证明与内核无关**，但谜团没解开——下篇靠换术式绕过了它 |
| 8 | 方向 = 优化"USB 加载内核"这条临时链路 | 一直在打磨 ATAGS 桩、解压器、预留表 | 用户直接点破 | 用户要的是 **NAND 自启动**，见第七章 |

> 其中第 6 条和第 7 条是**最贵的两条**：为了它们花掉了整整一晚。事后看，正确做法是"先确认官方镜像三件套在不在，再决定要不要碰内核二进制"。
